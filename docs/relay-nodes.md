# 中转节点：单入口、多逻辑节点、多落地出口

一个 VLESS 或 Hysteria2（HY2）入口节点加若干落地节点，在订阅里表现为多个可以直接选择的普通节点。
所有节点共用入口的客户端协议、传输方式、地址、端口和传输安全参数。客户端
不需要代理链，也看不到任何落地服务器的连接信息。

面板 `1.11.0` 与 Node `v1.13-yz.21` 的源码实现支持 Xray、sing-box 入口和落地混用。
面板 `1.12.0` 与 Node `v1.13-yz.22` 进一步支持开启 ECH 的 HY2 入口。
面板 `1.12.1` 生成客户端订阅时按入口内核判断 sing-box 多路复用，避免混合内核中转误用落地的内核选择；数据库中的落地配置不变。
发布引用、固定核心依赖与验证状态见 [兼容矩阵](../YZ_COMPATIBILITY.md)。

## 前置入口的含义

节点管理页面的编辑表单里有一个独立的“前置入口”下拉，位于“父级节点”之后。

- 前置入口为空：普通节点，行为不变。
- 前置入口不为空：当前节点是中转逻辑节点，前置入口是客户端实际连接的真实入口。

**它与“父级节点”完全独立。** 父级节点保持上游语义（共享运行状态、共享 SS2022 服务端
密钥），不参与中转判定；中转关系只看前置入口。一个节点可以同时设置两者，互不影响。

分成两个字段是因为父级节点下拉只列出同协议的节点，而前置入口可以是 VLESS 或 HY2，落地可以是
Shadowsocks 或 VLESS，不能用原字段完整表达。前置入口下拉列出「没有前置入口、配置有效的 VLESS 或 HY2 节点」，
支持 Xray 和 sing-box，候选能力由后端统一判断。

对于中转逻辑节点，各字段的含义变为：

| 字段 | 含义 |
| --- | --- |
| 协议 | 入口到落地之间的内部协议，支持 Shadowsocks 和 VLESS |
| 节点地址、连接端口 | 入口连接落地服务器时使用的地址和端口 |
| 服务端口 | 落地服务器上内部入站的监听端口 |
| 绑定服务器 | 最终落地服务器 |
| 节点名称、排序、权限组、显示、启用 | 逻辑节点自身独立拥有 |
| 倍率 | 不生效，强制继承入口节点 |

约束：

- 前置入口必须是配置有效的 VLESS 或 HY2 节点，且自身没有设置前置入口；
- 不允许节点以自己为前置入口、多层中转，或让已经是别人入口的节点再设置前置入口；
- 已被落地引用的入口必须保持有效的 VLESS/HY2 配置；切换内核时会检查已有落地的内部协议是否兼容；
- Shadowsocks 落地的加密算法必须在支持列表内；
- VLESS 入口和落地必须符合下文的传输与安全组合，H2 不受支持。

违反以上任一条时，保存节点会返回“前置入口”的校验错误。

## 路由编号

面板为每个节点自动分配一个 1-65535 的路由编号，管理员无需填写。数据库仍沿用
`vless_route` 字段。生成订阅时，编号被写入 VLESS 身份或 HY2 认证 UUID 的第 7、8 字节
（标准写法的第三段）。Xray 校验用户前会把
这两个字节清零，因此不影响身份匹配；认证通过后再按原始字节还原编号，用于选择出站。

sing-box 入口为每个用户和线路生成独立认证身份，使用原生 `auth_user` 规则选路，随后把
线路身份映射回真实用户。订阅格式与 Xray 相同；客户端无需增加特殊功能。
sing-box 未注册的线路编号会认证失败，已删除或轮换的身份也不能通过旧 HY2 会话发起新请求。

编号在创建时分配并保持稳定，编辑节点不会改变。分配游标只增不减，删除节点后编号
不会被立即复用。编号 0 不使用，因为 Xray 的端口列表解析会丢弃数字 0。

## HY2 前置入口

面板 `1.10.0` 与 Node `v1.13-yz.20` 起支持“客户端 → HY2 前置入口 → Shadowsocks/VLESS 落地”。
Node `v1.13-yz.21` 固定使用 YZ-Xray-core `v26.7.11-yz.6`，包含 VLESS 首批缓冲上传计数、UDP 缓存与 HY2 会话关闭同步修复；
sing-box 配套 `v1.14.0-yz.2`，原 SS2022 模块的关闭补丁随 Node 发布，整体验证见 [兼容记录](../YZ_COMPATIBILITY.md)。

1. 创建入口节点，内核选择 `Xray` 或 `sing-box`，协议选择 `Hysteria`，版本选择 `2`，配置入口地址、UDP 端口和有效证书。
2. 创建 Shadowsocks 或 VLESS 落地节点，填写入口到落地的连接参数，并在「前置入口」中选择该 HY2 节点。落地可以独立选择内核。
3. 客户端刷新订阅后选择相应逻辑节点。各节点连接同一 HY2 入口，认证值自动包含各自的路由编号。

HY2 入口终止客户端的 QUIC/TLS 连接，从认证信息恢复真实用户和编号，再选择内部出站。
路由在一个 QUIC 会话内保持固定；同一用户选择不同落地时使用各自的认证值建立会话。
标准 HY2 客户端无需识别编号，也不需要额外的代理链配置。

入口支持可选的 Salamander 混淆，密码至少 4 字节；带宽和混淆参数随订阅继承。
HY1 不作为中转入口。入口自身仍可选择直接出口，普通 HY2 节点的认证值不改写。
路由优先级沿用现有 VLESS 中转规则。Xray 未匹配编号时使用默认出站；sing-box 只接受已经下发的线路身份。

### HY2 入口开启 ECH

需要配套面板 `1.12.0` 和 Node `v1.13-yz.22`。发布后应先更新 Node，再更新面板并使用新的入口候选，
旧版 Node 的中转校验仍会拒绝 HY2 ECH。入口保留正常的 TLS 证书和服务名，再启用 ECH、生成或填写配对的
服务端密钥与客户端公共配置。服务端密钥缺失的入口不会进入候选；Node 在启动时检查实际密钥文件及格式。

面板将入口的 `protocol_settings.tls.ech` 下发为 Node 的 `tls_settings.ech`。
Node 为 Xray 写入 `tlsSettings.echServerKeys`，为 sing-box 写入 `tls.ech.key` 或 `key_path`。
ECH 只终止在 HY2 入口，入口到落地继续使用原有 VLESS 或 Shadowsocks 配置。

| 订阅格式 | HY2 ECH 参数 | 使用条件 |
| --- | --- | --- |
| sing-box JSON | `tls.ech.enabled`、PEM 数组 `tls.ech.config`、可选 `query_server_name` | 实测客户端内核为 `1.14.0-yz.2`；沿用现有 sing-box 版本规则 |
| Mihomo YAML | `ech-opts.enable`、Base64 `ech-opts.config`、可选 `query-server-name` | 内联配置实测官方 Mihomo `1.19.9`；只靠查询域名获取配置需要 `1.19.20`；已知内核低于对应版本时过滤 |
| 通用 HY2 URI、其他客户端格式 | 本次未增加 ECH 字段 | 不将其视为已验证的 ECH 订阅，使用上面两种格式完成 ECH 连接 |

Clash Verge 等应用需要确认内嵌的 Mihomo 版本，应用版本本身不能直接换算为内核版本。
面板 `1.12.1` 起同时识别 `mihomo` 和 `meta`，并区分基础 ECH 与 DNS 查询域名的最低版本。
只指定 `flag=meta`、`flag=mihomo` 而没有版本信息时仍保留节点及 ECH 参数，由用户确认客户端内核支持。
字段转换、版本规则和 XHTTP 支持范围见 [Mihomo 订阅兼容说明](mihomo-subscription.md)。
两种已支持格式只输出公共配置，不输出 ECH 服务端密钥或本地文件路径。公共配置为空时可保留 DNS 查询域名；
本次实际握手验证使用内联公共配置，没有验证外部 DNS 记录的部署。

验证覆盖 ECH 接受状态、错误公共配置拒绝、TCP/UDP 三路选路、Salamander、用户增删、重复同步、
ECH 密钥轮换、停止恢复，以及用户流量只累计一次。具体范围见 [HY2 ECH 验证记录](hy2-ech-validation.md)。

## 订阅生成

中转逻辑节点在订阅中继承入口的客户端协议、传输方式、地址、端口和传输安全参数，保留
自己的名称、排序、权限组和显示状态，并使用当前用户的原始 UUID（只改写路由字节）。
入口节点本身继续作为可见、可选择的节点存在，使用本机直接出口。

以下情况逻辑节点不会出现在订阅中：

- 用户所在权限组不在该逻辑节点的权限组内；
- 节点被禁用；
- 拓扑不完整，例如前置入口已被删除。

拓扑不完整时节点会被直接丢弃，不会退化成一个暴露内部地址的普通节点。

## 服务器之间的中转

入口服务器上的 Xray 或 sing-box 为每个逻辑节点生成一个独立的 Shadowsocks 或 VLESS 出站，按路由编号选择；
落地服务器上的内核生成一个只含内部凭据的对应入站，收到请求后直接访问目标。
不使用 Realm、GOST、NodePass、WireGuard 或 iptables 端口转发，落地服务器也不需要开启
系统级转发或出口地址转换。

内部认证信息由面板从应用密钥派生，两端各自从面板拉取，不落库、不写入订阅、不写入日志。

### VLESS 有效组合

以下矩阵适用于 Xray VLESS 入口，以及两端均为 Xray 的 VLESS 内部链路，按当前固定的
YZ-Xray-core 能力校验：

| 传输 | 无传输安全 | TLS | Reality |
| --- | --- | --- | --- |
| RAW / TCP | 支持 | 支持 | 支持 |
| WebSocket | 支持 | 支持 | 不支持 |
| gRPC | 支持 | 支持 | 支持 |
| XHTTP | 支持 | 支持 | 支持 |
| HTTPUpgrade | 支持 | 支持 | 不支持 |
| mKCP | 支持 | 支持 | 不支持 |
| Hysteria | 不支持 | 支持 | 不支持 |

sing-box VLESS 入口或任一端使用 sing-box 的内部链路，支持范围如下：

| 传输 | 无传输安全 | TLS | Reality |
| --- | --- | --- | --- |
| RAW / TCP | 仅内网 | 支持 | 支持 |
| WebSocket | 仅内网 | 支持 | 不支持 |
| gRPC | 仅内网 | 支持 | 支持 |
| HTTPUpgrade | 仅内网 | 支持 | 不支持 |

sing-box 中转不支持 XHTTP、mKCP、Hysteria 传输、VLESS Encryption 和 TCP 头部伪装。
Vision 只允许 RAW/TCP 配合 TLS/Reality。选择公网 VLESS 落地且任一端为 sing-box 时，
必须启用 TLS 或 Reality。Shadowsocks 落地仍可在两种内核之间混用。

补充约束：

- H2/HTTP 传输已由当前 Xray 移除，管理端不再显示；需要类似能力时使用 XHTTP；
- mKCP 的旧 `header` 和 `seed` 已由当前 Xray 移除；
- Flow 只允许留空或 `xtls-rprx-vision`，旧的 `direct`、`splice` 不再显示；
- 公网地址在不使用 TLS/Reality 时必须启用 VLESS Encryption；内网地址可显式使用 `none`；
- VLESS 中转暂不接收 ECH 和 `allowInsecure`，避免生成当前核心无法启动或无法完成客户端验证的配置；
- Hysteria 是 VLESS 的传输层，面板会为两端派生同一份内部 transport auth，管理员不需要填写。

### VLESS Encryption 与 xboard-node

VLESS Encryption 仅适用于两端均为 Xray 的链路。xboard-node 不需要单独配置，也不在本地保存密钥对。使用步骤如下：

1. 在作为落地的 VLESS 节点编辑页打开「VLESS Encryption」。
2. 点击 `decryption` 输入框右侧的钥匙按钮。管理端会复用 Reality 的浏览器端 X25519
   生成器，一次填入配对的 `decryption` 和 `encryption`，每次点击都会生成一组新内容。
3. 检查后保存节点。点击按钮只修改当前表单；保存前关闭或取消编辑不会下发密钥。
4. 如果需要 ML-KEM-768 而不是自动生成的 X25519，可继续使用兼容 Xray 手工生成：

   ```bash
   xray vlessenc
   ```

   把命令输出的 `decryption` 填入服务端字段，把同一组的 `encryption` 填入客户端字段；
   X25519 组或 ML-KEM-768 组二选一，不能交叉混用。
5. 保存后，面板只把 `encryption` 发给入口出站，把 `decryption` 留在落地入站；内部 UUID
   由面板派生。两台 xboard-node 在下次拉取或推送配置时自动重载，不需要修改 `config.yml`。

VLESS Encryption 可以与表中任一有效传输/安全组合叠加。使用 TLS 或 Reality 时它是可选的；
公网纯传输（安全模式为“无”）则必须启用。轮换时必须重新生成同一组的两项并在一次保存中
同时替换，不能只改其中一端。钥匙按钮会同时覆盖当前表单里的两项，因此点击后应保存或取消，
不要只复制其中一项到其它节点。

## 权限、倍率和流量

每个逻辑节点保留独立的名称、权限组、显示状态、启用状态、排序和节点总流量。

流量分成两个互不叠加的口径：

**用户套餐流量**只在入口按真实 VLESS/HY2 用户身份统计一次。用户通过任意逻辑节点产生的
上下行流量都计入入口上的同一份用户流量。扣除公式固定为：

```
用户扣除流量 = (入口统计到的上行 + 下行) × 入口当前生效的倍率
```

入口倍率为 2 时，用户产生 100 MiB 原始流量，套餐扣除约 200 MiB。入口流量与落地流量
不相加后再乘倍率，也不分别用入口倍率和落地倍率重复计算。逻辑节点自己填写的倍率不参与
用户扣费，读取和展示时统一使用入口的有效倍率。

**落地节点流量**由入口按各逻辑节点的实际内部出站归属，按稳定的出站标签
`relay-<节点 ID>` 映射回对应逻辑节点，只用于在控制面板查看各落地线路承载的上下行和总量，
不参与用户套餐扣费。落地服务器的内部入站没有面板用户，不会重复上报用户流量。

Xray 读取内部出站计数，可能包含协议封装；sing-box 按用户连接实际选中的出站累计 TCP/UDP
有效载荷。两种入口的节点总量口径可能不同，用户套餐扣费规则一致。
自定义规则把请求改为直连时，sing-box 不会把该流量归到原计划的落地。

面板 `1.9.0` 与 Node `v1.13-yz.16` 起还通过 `relay_user_traffic` 提供用户-逻辑节点的原始流量明细，
HY2 入口沿用同一报告字段。该明细不重复扣费，逻辑节点仍不能设置独立有效倍率。
用户总流量、剩余流量、速度限制和设备限制统一以入口上的用户身份为准。

## 生命周期

逻辑节点新增、修改、禁用或删除后，面板会同时刷新入口节点的配置，入口据此重新生成
内部出站和路由规则。重复同步、节点程序重启和配置重载保持幂等，不会产生重复的
入站、出站或路由规则。sing-box 的用户增删使用热更新，落地拓扑变化会按现有生命周期
重建入口实例，连接可能重新建立；用户与线路累计流量继续保留。

sing-box 生成的认证项数量为「用户数 ×（落地数 + 1）」。增加落地不会增加客户端监听端口，
但会增加配置与热更新的内存开销。

## 升级影响

启用 sing-box 中转前，先升级所有相关 Node 到支持该功能的版本，再升级面板并设置拓扑。
旧 Node 会拒绝 sing-box 中转配置；新功能不需要修改 Xray 或 sing-box 的固定依赖。

**存量节点不受影响。** 中转关系存放在新增的 `relay_entry_id` 列，升级后该列对所有既有
节点都是空的，因此不会有任何节点被识别成中转逻辑节点。父级节点（`parent_id`）的行为与
上游完全一致，没有改动。

`relay_entry_id` 为 0 或 NULL 都表示“不使用中转”，管理端把“无”提交为 0。

## 管理端界面

管理端是构建产物，前置入口相关的两处界面由构建阶段的定点补丁注入
（`.docker/patch-admin-relay.php`）：

- 节点编辑表单里的「前置入口」下拉，位于「父级节点」之后；
- 入口候选使用后端 `relay_entry_supported` 字段过滤，兼容 Xray 与 sing-box；
- 节点列表表头的「前置入口」列，位于「部署方式」与「地址」之间，显示该节点走哪个入口，
  未设置时显示 `--`。该列在拖拽排序模式下与其他数据列一同隐藏。
- VLESS 传输下拉移除 H2 和过时 Flow，增加 Hysteria，并禁用已知无效的 Reality/Hysteria 组合。
- VLESS Encryption 的 `decryption` 输入框加入与 Reality 私钥相同的钥匙按钮，在浏览器内
  生成 X25519 配对内容并同时填入两个字段；密钥在管理员保存前不会发送到面板或 Node。
- 节点列表的批量操作菜单按权限组提供「添加为」和「移除」动作，操作只增量修改目标组，
  不会覆盖节点已有的其它权限组。
- Shadowsocks 新建节点默认优先选择 `2022-blake3-aes-128-gcm`；已有节点的算法配置不变。

列显示的入口名称由 `GET /api/v2/admin/server/manage/getNodes` 的 `relay_entry_name` 字段
下发。名称在服务端用同一份全量节点列表解析，不额外查库，也不受列表搜索和筛选影响——入口
节点被筛掉时，逻辑节点这一列仍然显示得出来。入口已被删除时该字段为 null，显示与未设置一致。

该补丁匹配不到锚点时会让镜像构建直接失败，而不是产出一个缺少这些界面的管理端——所以升级
上游管理端产物后如果构建报这个错，说明补丁需要同步更新。产物只带有一半补丁标记时同样直接
失败，避免把表单字段重复注入第二遍。

补丁不修改原有的父级节点下拉和其他列。YZboard 补充界面的文案目前是硬编码的简体中文，
不随管理端语言切换。VLESS 组合的最终判定仍由面板保存校验和 Node 启动前校验共同完成。
