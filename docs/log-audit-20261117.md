## 优先处理：xTom-US² 到 Taipei101 落地不通

入口节点 456 的本机监听、默认出网以及其他已检查落地正常，但到节点 302（Taipei101-US 落地）的出站连续多个检查周期失败，每次约八秒超时。节点 302 自己的默认出网检查正常，Agent 在 TCP 34211 端口监听。

从 xTom-US² 对该端口做三次 TCP 连接，均在三秒超时；从 JCloud 对同一端口做两次连接，分别约 174、163 毫秒成功。落地端有来自 xTom-US² 的 SYN-RECV 连接，说明初始连接请求已到达，但握手尚未完成。

面板来源限制停用，落地 UFW 明确放行该 TCP/UDP 端口；落地回程路由有默认网关。xTom 连接跟踪数量为 181、上限 65536，没有表满证据。

**确认的是两台之间的 TCP 链路失败。** 现有证据将问题缩小到该路径、回包处理或源端收包过滤；尚不能定位哪一段丢包，也不能据此认定供应商或 Agent 程序有 Bug。下一步应关联两端同次连接的握手与丢包记录，再处理已经证实的原因。

## 面板代码：Lite 读取诊断缺失及同步等待风险

当天面板日志有 14 次 Lite 读取失败（502），均来自服务器列表的监控快照；另外有 4 次等待已有读取者超时（503）。最新记录为 16:45:36。

用生产配置在面板主机直接调用只读 Lite 接口，两个 IPv4 地址均返回 HTTP 200，认证、JSON-RPC 格式和结果类型有效。首次状态读取耗时约 7.036 秒，随后状态或服务器列表读取约 0.041–0.061 秒。抽查的一个 IPv6 地址连接失败。该结果排除了检查时的持续密钥或格式错误，不能反推此前每次失败的具体原因。

源码中的明确诊断缺口位于 `app/Services/LiteClient.php:51`：全部失败最终被替换成同一条通用提示，没有保留安全的连接错误分类、HTTP 状态或 RPC 错误编号；同时只尝试第一个已校验 DNS 地址。

另有同步等待风险：单次上游读取最多十秒，其他请求等待缓存结果最多十二秒，资料读取等待最多二十二秒。生产 Web 只有两个请求工作进程，管理端每十秒读取一次快照。慢读取和等待可能占用有限的请求处理能力；本次没有完整工作进程占用记录，**尚不能断言它导致了所有 Agent 超时**。

建议先补充脱敏后的错误分类、状态码、耗时和固定方法名称，再在共享总超时内评估地址回退；减少其他请求同步等待上游读取的时间，保持凭据、公网地址校验和监控数据时效规则。

### 健康检查日志

使用 Go 1.27.3、正式锁定核心依赖和正式功能标签，在本机通过临时 Go 文件映射增加两个复现场景，不向仓库写入测试代码，不使用生产身份、配置或监听：

1. 启动带独立 Reality 夹具的 sing-box 入站，执行与当前监听探测相同的 TCP 建连后关闭。连接成功，但事件出口产生 `REALITY: processed invalid connection` 的 error；同一核心随后通过正常出站收发检查。
2. 启动独立入口和 Shadowsocks 2022 落地，先探测不可用的回环 IPv6 端口，再探测同一出站的回环 IPv4 应答服务。落地首先产生真实的 IPv6 `connection refused` error，随后 IPv4 成功。该夹具用于证明失败尝试与最终成功共存，不用于模拟生产的每一种 IPv6 网络错误。

两个现象均成功复现。首轮中第二场景的 IPv6 请求被夹具安全规则拒绝，随后将该回环地址显式允许并重新验证，最终确认错误来自实际 IPv6 端口不可用。该结果证明：本机监听探测未完成应用握手，中转落地又无法从普通代理请求中识别入口端的健康探测，因而日志将预期的失败尝试记录为普通连接错误。

修复应分别处理：本机监听探测按具体探测连接识别；中转探测减少每轮重复尝试已经不可用的地址，例如选择合适的初始地址族或短期复用同一配置下的成功地址。若需要可靠地改变落地日志等级，还需明确的探测身份或上下文传递，单改入口上下文不够。应保留 IPv6 回退、真实用户错误和最终健康失败信息，不宜按回环地址、目标网站或错误关键词全局过滤。

本轮完成的是排查和复现，没有实施上述行为修复。临时测试和文件映射在交付前清理，四项协议检查不代表完整并发回归或所有线上请求通过；当前工作区原有日志优化等改动继续保留。
