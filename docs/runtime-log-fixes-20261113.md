# 运行故障修复

维护者：P0me1oo。日期：2026-11-13。面板 2.16.6、配套 Agent v2.37.1；已发布并部署至 Solid-US LA，见[发布](release-2.16.6.md)与[部署记录](deployment-2.16.6.md)。Agent 已发布，运行节点由用户自行更新。

## 设备锁竞争

生产排查发现设备完整同步在持有节点锁时等待账号锁，等待超时会返回 500。更新后集中重连时，WebSocket 工作进程的同步等待还会延迟其他节点的消息。

新版 Agent 在设备会话、准入、同步请求中发送 `lock_retry=1`。面板完成原有参数、身份与权限校验后，为这一次请求复制协调服务并使用非阻塞锁；遇到占用立即退出，释放本次已经取得的节点、账号或队列锁，返回 HTTP / WebSocket 503。HTTP 响应带 `Retry-After: 1`。未携带该能力声明的旧节点仍等待最多两秒，等待超时也返回 503。

Agent 仅对 503 作带抖动的有限退避，沿用同一业务序号、完整快照和鉴权，既不新建第二次申请，也不延长调用方的截止时间；一次接口调用上限为八秒。正常长连接继续使用原通道。403、409、412 等拒绝与会话处理保持不变。

快照写入和逐账号协调并不是一个整体事务。一次请求可以在写入节点快照后遇到账号锁占用，或在保存账号状态后遇到队列锁占用；此时不会返回成功许可。后续同序号重试继续核对当前权威状态、权限和队列，已归还的许可不会复活，未确认的归还不会提前释放名额。

锁竞争通过原始锁异常记录节点编号、操作和调用位置，按现有策略限频；HTTP 与 WebSocket 不再重复把同一次锁占用记为未知服务错误。其他异常没有被改为可重试状态。旧面板忽略新增字段，仍沿用原行为，因此可以先更新 Agent，再更新面板。

## DNS 诊断

近 24 小时的排查中，两个前置池累计 43 次 DNS 同步失败，均在下一轮恢复。原代码将底层原因替换为同一提示，并在调度入口吞掉异常，现有历史日志不足以确定全部失败的根因。

同步阶段和调度阶段现在分别记录池编号、异常类型、代码位置及脱敏原因；数据库错误只保留 SQLSTATE 和驱动错误码。不同前置池独立限频。锁超时显示“DNS 同步锁繁忙，稍后自动重试”；其他公开错误保持原安全提示。日志写入失败不覆盖同步结果，失败不更新最后成功时间，只有真正成功才记录恢复。

本次没有猜测性修改 DNS 锁、记录归属、外部 API 重试或调度频率。上线后需根据新增诊断确认生产失败是否确为同区域任务争锁。

## 验证

使用独立框架缓存路径、SQLite 内存库、仅监听回环地址的临时 Redis 8.0.2 和 MariaDB 11.8.6；MariaDB 开启 `ONLY_FULL_GROUP_BY`。生产数据库为不同版本，未作生产故障注入。

- SQLite 分批相关回归共 191 项、6,055 断言通过；包含真实 Redis 许可生命周期和八进程并发准入、身份撤销、实时接口、日志隐私、DNS 归属及恢复。
- MariaDB 分批相关回归共 129 项、5,591 断言通过；包含 DNS、设备 HTTP / WebSocket、真实 Redis 锁竞争与重试。
- 新增场景覆盖节点锁与账号锁忙时不确认成功、及时释放节点锁、原请求重放、权限撤销、不同池独立诊断、日志出口故障和 DNS 成功后的恢复标记。

Agent 与订阅插件的验证记录分别见其项目文档。本次无数据库迁移、管理端改动或核心依赖变化，未执行完整发布矩阵。

## 仍需服务器侧处理的 IPv6 问题

这些是先前只读检查确认的环境与出口约束，不会被本次程序修改自动修复：

| 机器 | 已确认状态 | 处理边界 |
| --- | --- | --- |
| Taipei101 美国 Lax4 | 内核启动参数禁用 IPv6 | 启用涉及启动配置及重启；如果继续仅支持 IPv4，应在客户端或路由策略避免提交 IPv6 目标 |
| BreadCloud 美国 | IPv4 正常，IPv6 到两个公共目标超时 | 需核对并修复 IPv6 上游路由；有 IPv6 地址和默认路由不代表出口可达 |
| JCloud 西班牙 | 没有 IPv6 默认路由 | 先确认供应商是否提供可用 IPv6，不能凭空新增网关 |
| Aether 美国 | 明确绑定 IPv4 出口并设置 ForceIPv4 | 属于现有出口约束，不能通过自动改用其他地址族绕过绑定 |

域名解析策略不能把已经传入的 IPv6 字面地址转换成 IPv4。没有修改这些机器的网络、客户端配置、启动参数或服务。

2026-11-14 后续处理：已完成 Lax4 与 BreadCloud-US 的服务器侧修复，两台默认 IPv6 出口均通过外网连接验证。Lax4 解除了内核、系统参数和 UFW 的禁用；BreadCloud-US 确认为默认源地址选择问题，固定使用可达的原生 IPv6 地址后恢复。详情及附加地址的限制见 [IPv6 修复记录](ipv6-repair-20261114.md)。
