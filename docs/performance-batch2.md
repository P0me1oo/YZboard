# 第二批性能优化

版本 `1.82.2`，开发基线 `0841f0a2028453872bac3adb99eddea011c80e0d`。开始时工作区已有第一批 `1.82.1` 优化，保留并一并交付；本批写入对比使用第二批开始前保存的七个写入类，不把第一批读取优化算入收益。正式发布状态见 [兼容矩阵](../YZ_COMPATIBILITY.md)。

## 入站 IP 历史

原实现已经在单次报告内按用户和规范化地址去重，并分块插入地址、合并每日历史。本批只减少剩余重复工作：同次报告中的原始地址只做一次规范化及排除判断；原事务内按固定顺序锁定相关地址和历史，只补建缺失地址、扩展确有变化的最早和最晚观察时间。同一时间范围内的重复上报及跨节点重复不再写入历史。

不增加跨上报缓存或缓冲。每次仍以数据库为准，清理地址、清理历史、恢复数据或事务回滚后都可以重新补建，不增加可见延迟。跨天、迟到、乱序、完整 IPv6、IPv4 映射与排除规则保持不变；不改变实时设备限制、准入或扣费。

每 256 条观察读取一次已有记录，插入和更新仍按 128 条分块。首次写入会多一次锁定查询；观察时间向前推进时仍需更新历史，因此并非所有输入都会减少 SQL。所有分块共用原事务，失败整次回滚，并保留死锁重试。

## 可靠流量批次

只处理已可靠保存的单个报告批次，不合并尚未保存的上报，不提前确认。按原用户、节点、入口、线路、倍率、统计种类及日期/小时/分钟维度归并已算好的整数增量，再分块原子累加；统计开关只在本次调用中读取并复用，失败重试重新读取。

用户及节点日账本保留模型写入和行锁；同用户同倍率的线路先按原规则分别乘倍率、取整，再合并日账本增量。批次锁、用户累计、完成标记、Redis 待检查集合及插件回调仍在原来的事务和处理顺序中。存在相关模型事件或服务扩展时保留逐项调用，避免改变回调次数和中间结果。重复批次不重复累计，分块、插件或 Redis 失败均不提交部分统计。

参考 Lite 的 `database/metricstore/report.go` 在一次写入中整理数据并集中提交的方式；没有引入跨批次状态缓存、额外队列或延迟落库。

## 验证与基准

使用 PHP `8.4.21`、独立 SQLite 内存库、仅监听本机的 MariaDB `11.4.8` 与 Redis `5.0.14.1`。受影响回归覆盖正常/重复/跨节点、日期和地址隔离、清理恢复、缓存故障、事务回滚、重试、倍率取整、统计启用边界、插件和旧数据。实际行锁和并发累加只在 MariaDB 验证；SQLite 不声称提供相同的行锁语义。

两批合并的本地 SQLite 相关回归通过 280 项、3,008 次断言；32 个改动 PHP 文件语法检查、五项管理端资源检查和差异空白检查通过。原会话已在 MariaDB 通过 98 项相关回归及新增并发检查。

[正式发布流程](https://github.com/P0me1oo/YZboard/actions/runs/38771649511) 使用 PHP `8.2.34`：SQLite 共 1,007 项、9,818 次断言，其中四项行锁并发检查按设计只在 MariaDB 运行；MariaDB `11.4.8` 严格分组完整回归 1,007 项、9,849 次断言全部通过，包含上述四项检查，管理端资源五项通过。双架构镜像与最新 Release 已核验，来源及摘要见兼容矩阵。本机无 Docker，未启动新镜像或部署到生产服务器。

基准入口为 `tests/Benchmarks/statistics-writes.php`。在相同的 128 个合成用户、两个规范化公网地址、三个节点、两台合成机器及线路输入下，串行运行修改前后实现，比较 SQL、事务、耗时、Redis 命令、集合内存、统计总量与逐行摘要。基准会重建专用本机测试库，不用于部署数据库。首次建库和样本准备不计入时间。

修改前七个类的副本已逐一核对，与开发基线 Git 文件内容完全一致，可从该固定提交提取到基准目录，通过 `YZ_BENCH_BASELINE` 选择；未设置时执行当前实现。MariaDB 基准设置 `YZ_BENCH_DB=mysql`、专用端口 `YZ_TEST_MARIADB_PORT`；Redis 使用独立本机端口 `YZ_BENCH_REDIS_PORT`，避免其他进程污染全局计数。临时 MariaDB 在前后测量中均使用每秒刷新事务日志的测试配置，不用该设置验证宕机持久性，也不修改生产配置。

SQL 计数不含开始/提交事务。SQLite 串行结果如下，修改前后统计总量、逐行摘要及入站观察边界一致：

| 输入 | SQL 前 → 后 | 耗时 ms 前 → 后 | 事务前后均为 |
| --- | ---: | ---: | ---: |
| 首次入站观察 | 3 → 4 | 59.037 → 41.905 | 1 |
| 相同观察重复 20 次 | 60 → 20 | 704.002 → 453.088 | 20 |
| 观察时间推进 20 次 | 60 → 60 | 713.429 → 962.064 | 20 |
| 首个流量批次 | 3,507 → 696 | 2,858.685 → 2,053.053 | 1 |
| 后续五个独立流量批次 | 17,515 → 3,460 | 19,260.606 → 7,500.151 | 5 |
| 重放已完成批次 | 2 → 2 | 4.516 → 2.024 | 1 |

SQLite 观察时间持续推进的本轮耗时上升，不能声称所有场景都更快。此时地址插入检查由锁定查询替代，SQL 次数相同；重复观察场景则完全省去写入。

入站路径的 Redis 命令前后都是零。首个流量批次前后各一次集合写入，后续五批各五次，重放为零；集合占用前后均为 335 字节，稳定阶段 Redis 内存增量均为零，PHP 进程峰值均为 46 MiB。初次分配的 Redis 全局内存增量会受分配器影响，不当作精确业务内存。原会话中并行运行基准时的 Redis 全局计数混入了其他基准，已弃用，以上使用独立实例串行结果。

| 输入 | SQL 前 → 后 | 耗时 ms 前 → 后 | 事务前后均为 |
| --- | ---: | ---: | ---: |
| 首次入站观察 | 3 → 4 | 69.904 → 28.031 | 1 |
| 相同观察重复 20 次 | 60 → 20 | 734.511 → 174.911 | 20 |
| 观察时间推进 20 次 | 60 → 60 | 1,280.386 → 364.333 | 20 |
| 首个流量批次 | 3,505 → 694 | 5,275.943 → 1,111.807 | 1 |
| 后续五个独立流量批次 | 17,515 → 3,460 | 24,228.253 → 6,967.304 | 5 |
| 重放已完成批次 | 2 → 2 | 3.174 → 1.508 | 1 |

这些是同一组合成输入的单轮测量，耗时会受运行环境影响；没有测量任意规模、地址全部不同或生产完整请求的成本。合成耗时不是生产 CPU 降幅，也不代表真实服务器部署后的整机收益。事务次数不减少，减少的是批次内的重复 SQL 和写入。
