## 账号操作

- 私聊机器人发送 `/start`。未绑定时提示发送本面板订阅链接；已绑定时展示主菜单。
- 链接必须能唯一匹配仍存在的 XBoard 用户。允许订阅已过期的账号绑定；旧 Token 被重置后不能再用于首次绑定。
- 一个 Telegram 用户与一个 XBoard 用户分别最多有一条新模块绑定，不能覆盖或抢占已有关系。
- 绑定后主菜单显示「订阅信息」「账户信息」「入站 IP」「流量记录」四个内联按钮。订阅详情直接展示当前链接，并提供「重置订阅」「返回主菜单」按钮；旧消息的「订阅链接」按钮也会打开这份详情。订阅链接每次按当前账号重新生成。
- 订阅详情按「套餐、状态、到期时间、已用 / 总量、剩余、进度条、重置倒计时」顺序展示。流量统一使用 GB 并保留两位小数，百分比保留一位小数，进度条共十四格；流量超额时进度条最多为 100%，剩余最少为零。长期有效账号的到期时间显示「长期有效」。
- 重置倒计时使用账号实际保存的重置日期，剩余天数向上取整，显示为「流量重置时间：x天」。无自动重置安排时显示「不自动重置流量」，已到安排日期时显示「已到流量重置时间」，不把到达日期当作已完成重置。查询不会重置流量或修改日期。
- 订阅状态按「封禁中、已过期、未开通、流量耗尽、即将到期、正常」的顺序判断，同时满足多个条件时只显示优先状态。尚未到期且剩余时间不超过 72 小时（含恰好三天），有可用流量时显示「即将到期」；到期那一刻起显示「已过期」。长期有效的订阅不显示「即将到期」。
- 账户状态只显示「封禁中」或「正常」，根据账号是否被封禁判断；余额只显示金额，没有状态分类。
- 在订阅详情点击「重置订阅」后，需要再点击「确认重置」。沿用用户页面的重置规则，更换订阅链接和节点连接凭据，再显示含新链接的订阅详情；取消后返回订阅详情。旧链接和旧连接凭据失效，需要用新链接更新客户端订阅。Telegram 绑定、套餐、到期时间、已用流量、余额和旧接入绑定保持不变。
- 重置确认五分钟内有效且只能使用一次。取消、过期、再次发起确认或重新绑定后，旧确认失效。回复失败时可重试；重复点击或 Telegram 重复投递不会再次更换订阅。也可重新打开「订阅信息」查询当前新链接。
- 账户信息显示邮箱、当前套餐、账户状态、余额和注册时间，未订购套餐时明确显示；提供解除绑定，也可发送 `/unbind`。确认有效期为五分钟；取消、过期、已使用或重新绑定前生成的确认不能解除后来的关系。
- 群聊不执行账号操作。每次文本或按钮操作都按实际 Telegram 发送者重新查绑定，不能通过按钮参数选择其他用户。

链接仅在首次绑定时用作身份凭据。续费、流量重置、套餐变化、订阅地址或 Token 变化、订阅过期、机器人停用以及配置变更都不会删除绑定。用户单个或批量删除时，由数据库级联清理该用户的绑定；重新注册同一邮箱不会继承旧绑定。

## 入站 IP 与流量记录

私聊发送 `/start`，点击「入站 IP」或「流量记录」；也可直接发送 `/ips`、`/traffic`。默认查询今天，可切换近 7 天、近 30 天，每页五条，支持上一页、下一页、刷新和返回主菜单。日期与出现时间使用消息中标出的面板时区，近 7 / 30 天包含今天。切换日期回到第一页；刷新和翻页按当前日期重新取数，旧页码超出结果时回到最后一页。

- 入站 IP 跨日期按完整地址去重，显示归属地、网络名称、ASN、所选时段的首次和最近出现时间。同一 IPv6 网段内的不同地址分别保留，当前前置地址排除名单在统计和分页前生效。位置查询失败时仍展示 IP 和出现时间，缺少的信息显示「未知」；位置来源、缓存和保留期沿用 [入站 IP 统计](statistics.md)。这些时间是面板收到上报的时间，不是每条连接的精确建立或断开时间。
- 流量沿用管理端用户明细，按日期、节点、直连或中转、当时倍率分别成行，按实际总量降序展示。每行包含实际上传、下载、总量以及扣费上传、下载、总量；顶部合计覆盖所选时段全部记录。倍率变化与零倍率分别保留，扣费读取当时记录，中转不会与入口重复累计。
- 已删除但保留名称的节点显示历史名称和「已删除」。早期已删除且无法恢复名称的节点沿用管理端规则，不展示明细，但保留其用量合计；有用量而无可展示明细时单独说明，不显示为零流量。少量用量使用 B、KB 或 MB，避免被两位小数的 GB 掩盖。
- 查询不改变账号流量、余额、重置日期或节点配置。每次操作重新读取发送者的绑定，按钮不接受用户编号；未绑定时引导绑定，群聊只提示私聊。发送失败可按原消息重试，重新绑定后未发出的旧查询失效，已完成投递的重复消息不会再次发送。

新版本部署后，已有绑定无需重建，发送 `/start` 即可显示新按钮。快捷命令立即可用；Telegram 的斜杠菜单在下一次从管理页面启用机器人时登记新命令，无需为了使用查询功能停用机器人。没有积累的数据不从在线缓存或账号累计用量反推。

## 链接识别

支持面板配置的订阅域名、域名中的数字范围和随机标识模板，以及以下两种订阅形式：

- 当前订阅路径：面板设置的订阅前缀加账号订阅标识。
- 旧订阅接口：`/api/v1/client/subscribe` 的订阅查询参数。

只在本地解析链接并查询数据库，不访问用户提供的网址，不展开短链。不接受任意外部域名、裸订阅标识、重复或数组形式的订阅参数，以及带账号密码的 URL。插件自行改写为其他凭据或未支持路径的链接，暂不能用于首次绑定；这不影响已经建立的绑定。

## 管理页面

配套代码完成部署后，入口为「系统管理 / Telegram Bot」，不在插件管理中。

### 机器人设置

1. 填写机器人密钥，确认消息接收地址是当前面板可访问的 HTTPS 地址。
2. 已保存密钥默认显示星号，星号只是占位，不作为密钥提交；没有新输入时保留原密钥。眼睛开关可显示正在输入的密钥；没有新输入时，点击后单独读取已保存密钥。查看不会触发保存，关闭或离开设置后隐藏。
3. 密钥框在启用期间也可以编辑。点击「保存」前检查密钥格式与 HTTPS 地址；如果当前机器人仍在运行或接收地址尚未确认撤销，先弹出确认，再自动停用旧机器人并保存新配置。取消不执行停用或保存，停用失败不提交新配置；停用后保存失败保留旧密钥和新输入，但机器人已经停用，可重试保存。保存成功后需要重新启用，已有账号绑定保留。已停用时保存仅写入配置，不向 Telegram 发起请求。
4. 打开、刷新页面或返回「机器人设置」时自动查询 Telegram，更新相邻排列的运行状态与机器人账号和错误提示；也可点击「验证连接」主动检查。页面不再展示待投递消息、消息接入及最近收到消息三个统计项；地址登记仍不能证明实际消息已到达。
5. 点击「启用」并确认，才注册消息接收地址和私聊命令。发现该机器人已有其他接收地址时拒绝静默覆盖。
6. 停用同样需要确认。停用保留绑定，不主动丢弃待处理消息，也不会删除已经归其他接入使用的接收地址。

同一个 Telegram 机器人只能使用一个消息接收入口。若复用旧机器人，需要先明确停用旧接入；本模块不会擅自关闭旧插件、接管机器人或迁移历史绑定。

### 测试发送与故障定位

- 在「测试接收人」填写 Telegram 数字 ID，不能填 `@用户名` 或群组 ID；接收人须先在 Telegram 私聊该机器人发送 `/start`。即使接收地址故障、没有面板绑定记录或机器人本地未启用，也可使用已保存的密钥测试发送。
- 点击「发送测试消息」后，只发送固定测试文字。Telegram 返回对应私聊消息的确认结果后才提示成功；成功发送后十秒内禁止重复测试。失败可重试，输入保留。
- 测试发送不写入接收时间、不建立账号绑定，也不修改或重新登记消息接收地址。看到测试消息只能确认面板能够向 Telegram 发消息；回复 `/start` 才能继续检查反方向。
- 自动检查使用已保存配置，不覆盖表单里未保存的内容或测试接收人。经过分类的最近一次失败原因仍显示在页面上，常见类别包括 HTTP 拒绝、路径不存在、服务错误、证书、域名解析、超时和连接被拒绝；检查失败后仍可停用机器人。正常页面不再提供「刷新状态」按钮，读取失败时保留「重试」。
- 只有接收地址匹配时才显示该地址的投递错误。没有待投递消息、且面板收到消息的时间晚于 Telegram 记录的错误时，下一次检查清除历史告警；待投递消息仍存在时保留告警。远端错误原文不保存或回显，以免夹带认证信息。

若私聊发送 `/start` 后没有回复，刷新页面查看投递错误：HTTP 403 需要区分入口拦截与来源校验失败，HTTP 404 检查路径和反向代理，HTTP 5xx 检查面板服务日志。具体服务器原因必须以实际诊断结果为准，不能仅凭地址登记成功判断。

启用期间以及注册结果未确定时，更换密钥必须先完成停用；新版页面在确认保存后自动完成这一步，后端仍拒绝绕过停用直接覆盖配置。消息接收地址在启用期间仍不可编辑。网络失败导致停用未确认时可重试；如果 Telegram 明确返回旧密钥已失效，则停止本地接收并允许保存新密钥，但不能声称远端地址已经移除。新密钥启用前仍会重新核对接收地址。

### 用户管理

进入页面或重新进入「用户管理」时自动查询最新绑定列表；按邮箱、Telegram ID 或用户名查询，分页显示账号、Telegram ID、Telegram 用户名、绑定时间和解绑操作，保留页码，不显示绑定总数文案。用户名显示为 `@用户名`，支持带或不带 `@` 的部分匹配、不区分大小写，下划线按原字符匹配。桌面表格和手机卡片均显示用户名，未获取或未设置时显示「—」。该页面使用面板管理员权限；普通用户无法调用这些管理接口。

每个用户提供「解绑」按钮。确认框显示邮箱、Telegram ID 和用户名，确认后解除该条关联；取消不执行，提交期间防止重复点击，失败时保留目标供重试。成功后重新查询列表，保留搜索条件，末页为空时回到最后一页；读取失败显示重试入口。

解绑保留面板账号、套餐、余额、流量、到期时间、订阅链接和节点凭据，也不改动旧 Telegram 接入的关联。无需机器人启用或连接 Telegram。管理员接口 `POST /api/v2/{管理路径}/telegram-bot/unbind` 只接收所选关系编号（`binding_id`），已不存在的关系按成功处理；旧页面或重复请求不会删除重新建立的新关系。原关系的短期解绑与订阅重置确认随关系一起清除；消息防重记录保留，重复投递旧绑定消息不会恢复关联。用户可重新发送有效订阅链接建立新关系。

用户名在绑定时保存，随后随有效私聊文本或按钮操作更新；改名会替换旧值，移除用户名会清空。仅使用消息发送人或按钮操作者的资料，不读取机器人自己的用户名。旧绑定在下次互动时补齐，无需解绑重绑；不批量请求 Telegram 回填。用户名可修改或不设置，账号关系继续使用数字 ID，绑定时间不受影响。重复投递的消息、超过有效期的文本、群聊和身份不匹配的消息不会更新资料；异常格式不覆盖已知用户名。

## 数据与消息处理

### 主动提醒（随 1.48.0 发布）

管理入口为「Telegram Bot / 提醒设置」。管理员分别开启到期、过期、设备数超限、连接数超限四项提醒，用户端没有关闭入口。提醒设置通过独立管理员接口保存，不停用机器人，不修改机器人密钥或消息接收地址。机器人停用期间不产生或发送新提醒。

- **到期提醒**：默认提前 3 天，可设 1–365 天。剩余时间进入所设范围时发送一次，按当前到期时间持久化防重；开启时已经进入范围但尚未过期的用户也会提醒。长期有效、未开通、没有新模块绑定的账号不发送。续费改变到期时间后按新的时间重新计算；发送前发现已经续费或过期，取消旧提醒。缩短提前天数时，尚未发送的提醒等待新窗口。
- **过期提醒**：每个到期时间发送一次。首次开启以及关闭后重新开启，都以本次开启时刻为起点，不补发此前已经过期的账号；过期后才绑定的用户不补发。保持开启时修改其他设置不会重置起点。短时定时任务或队列故障恢复后可以补处理开启期间发生的到期；机器人整体停用后重新启用也沿用该起点。
- **设备数超限提醒**：以节点实际拒绝新来源的上报为准，不把在线设备数达到上限当作已超限。`1.62.0` 配套 Node `v2.10.1` 后，显示拒绝发生时间、设备上限、已占名额、被拒绝的 IP 和「占用名额的 IP」，不再显示容易误解的周期拒绝次数。每条快照对应本上报周期首次记录的一次拒绝，不把周期内不同时间的名单拼在一起。
- **连接数超限提醒**：同时包含并发连接和每秒新建连接速率。同一批上报同时触发两种时合并为一条，但各自保留发生时间、上限和 IP 快照；并发展示「占用名额的 IP」，速率展示「已连接的 IP」，不将速率额度解释为设备名额。二者仍共用「连接数超限」冷却时间。
- **IP 信息**：被拒来源显示对应快照的一条地址；已连接来源去重后最多展示 5 条，更多时注明未展开数量。设备快照使用实际准入所依据的跨节点来源，连接快照使用该节点的已有连接。IPv6 完整来源与名额数可能不同，旧设备协议只有 `/64` 网段时保留网段标记。旧 Node 未提供快照时显示上报时间及可用的被拒地址，占用来源显示「未提供」，不查当前在线名单补造旧状态。
- **归属与引导**：发送任务复用在线设备的地区、运营商及 ASN 查询，沿用缓存、额度、超时和本地回退；查询失败显示未知，不阻断 Telegram 提醒，不在节点上报请求内查询外部服务。统一增加误报反馈和陌生 IP 可能意味着订阅泄露的提示，重置路径为「Bot → 订阅信息 → 重置订阅」。设备提醒保留减少设备或网络后重试的建议，连接提醒提示减少连接或新建频率。本次不新增流量或 IP 日志查询菜单。
- **超限间隔**：默认 60 分钟，可设 1–10080 分钟。按绑定用户和提醒大类分别计时，跨节点共用；设备与连接互不影响。以成功发送时间计算冷却，冷却期间不发送、不累计补发；结束后需要新的超限事件才再次提醒。事件有效期取当前间隔与五分钟中较长者，避免一分钟间隔在下一轮定时任务前就失效；过期的排队事件取消。重复上报和队列重复执行不会重复发送已完成的记录。

新接口 `POST /api/v2/{管理路径}/telegram-bot/reminders` 接收四项布尔开关以及提前天数、间隔分钟数，返回当前配置；由管理权限、输入校验与现有审计保护。配置读取接口同时返回这些非敏感设置。

新增 `v2_telegram_bot_reminders` 表保存绑定编号、提醒类型、到期时间、发送状态、重试时间及必要的超限数字。到期类按「绑定、类型、到期时间」唯一；超限类每个绑定每类复用一条记录，保留成功发送时间。记录随解绑或删除账号级联删除；到期防重记录在绑定存在期间保留，清缓存或重启不重发。`1.62.0` 在原事件详情中暂存上述 IP 快照，不新增数据库表；成功、取消或终止重试后清空，定时任务在机器人停用期间也清理过期快照。暂时失败的重试继续使用原快照，不作为 IP 历史日志保存。

每分钟执行 `telegram-bot:send-reminders` 检查到期状态，并向现有 `send_telegram` 队列派发待发送记录。节点上报只保存待发送记录，不在上报请求内连接 Telegram。部署沿用现有 Laravel 定时任务与 Horizon 队列，不增加服务器服务。旧插件的超限事件钩子保留；若旧插件也配置了提醒，应由管理员自行避免重复接入。

发送前重新检查绑定、开关、到期时间和事件时效。网络或临时服务错误按 1、2、4、8 分钟间隔重试，最多尝试 5 次；明确的无效请求、密钥失效或拒收立即终止该条提醒。失败不记为发送成功，也不阻止其他用户发送；超限类可在失败冷却结束后由新的事件再次触发。没有 Telegram 私聊成功确认时不记成功。

数据库与 Telegram 之间没有原子事务：Telegram 已发送但响应丢失，或发送后数据库提交失败，重试仍可能产生重复消息，不能承诺外部投递严格一次。正常响应、重复任务、重复上报及进程重启的防重由持久化记录负责。

### 管理员通知（1.67.0）

入口为「Telegram Bot / 管理员通知」，复用本模块的机器人。用户设备数超限通知、用户连接数超限通知默认关闭，与发给用户的提醒分别保存；受影响用户不需要绑定 Telegram。设置项及管理员消息标题在 `1.68.4` / 管理端 `0.41.4` 中统一采用这两个名称，尚未发布。此次只提供这两类告警，不增加工单、订单或任意消息群发。

填写管理员的 Telegram 数字 ID，每行一个，最多 20 个不同的接收人；也支持空格、中英文逗号分隔。不接受用户名、群组 ID 或重复 ID。接收人需先私聊机器人发送 `/start`，可在「机器人设置」逐个发送测试消息，然后启用机器人及所需告警。开启任一告警时至少填写一个接收人；两项关闭时可清空列表。保存告警设置无需停用机器人。

触发以节点实际上报的新设备、并发连接或每秒新建连接被拒绝为准。例如上限 100、已有 100 条正常连接但没有新连接尝试时，不发送告警；新连接因为限制被拒绝时才告警。设备名额满后成功替换旧来源的正常换网不作为拒绝告警。消息包含面板名称、用户邮箱及编号、节点名称及编号、限制类型、上限、发生或上报时间，以及节点提供的被拒 IP 和占用快照。沿用用户提醒的 IP 展示、归属查询与旧 Node 回退规则，不用当前名单补造历史快照；管理员消息不包含要求管理员自行重置订阅的用户提示。

重复告警间隔默认 60 分钟，可设置 1–10080 分钟，按「受影响用户、接收人、告警大类」分别计时，跨节点共用。设备与连接互不影响；同批并发和新建速率限制合并为连接告警。以成功发送时间开始冷却，冷却期间不累计补发，结束后需要新的拒绝事件。各接收人独立重试，已收到告警的人不会因其他人失败再次收到。机器人停用会取消尚未发送的管理员告警，重新启用不补发这些旧事件；移除接收人、关闭告警、删除用户或事件过期后，旧任务不能继续投递。

管理员设置接口为 `POST /api/v2/{管理路径}/telegram-bot/admin-notifications`，由现有管理员权限和审计保护。新增迁移保留机器人配置及用户绑定，并增加管理员配置和独立告警表（`v2_telegram_admin_notifications`）；发送成功、取消或终止重试后清空 IP 详情，只保留冷却及发送状态。用户删除时级联清理告警，移除接收人时删除其记录。

沿用每分钟定时任务及现有 Telegram 队列，节点上报请求只登记告警，不连接 Telegram。管理员私聊按每秒最多一条分散投递，并与用户提醒共用发送额度；临时失败最多尝试五次。事件有效期为当前告警间隔与五分钟中较长者，过期事件取消。数据库与 Telegram 的外部投递限制同上，不能承诺响应丢失时严格只发送一次。本次无需升级 Node 或代理核心；本地模拟测试不代表真实 Telegram 投递验证。

### 账号与消息记录

新增三张主应用数据表，不放入插件迁移：

- 机器人配置（`v2_telegram_bot_configs`）：密钥使用现有应用加密密钥加密存储；普通配置和操作接口只返回是否已配置及非敏感状态。管理员点击眼睛时通过独立接口读取密钥，该响应禁止缓存，前端不把它写入配置查询缓存或浏览器持久存储。
- 账号绑定（`v2_telegram_bot_bindings`）：保存用户编号、Telegram ID、最近一次有效私聊互动获取的用户名、绑定时间和各自独立的短期解绑、重置确认；确认内容加密存储，普通模型输出隐藏。两端分别设置唯一约束；用户外键使用与现有用户主键一致的有符号整数类型，并启用删除级联。`1.41.0` 增加两个可空的重置确认字段；`1.44.0` 增加可空的用户名字段，均不删除或重建绑定。用户名更新与本次业务处理、防重记录在同一事务内提交，回复失败后的重试不会重复覆盖资料。
- 消息处理记录（`v2_telegram_bot_updates`）：按机器人与消息编号防重，只保存动作、账号绑定记录编号和处理时间，不保存原始消息、订阅链接或订阅 Token。

绑定、订阅重置及业务处理状态在同一事务内提交。发送失败可以重试，但已经完成的绑定、解绑或订阅重置不会再次应用。重置通过用户模型保存，沿用现有节点同步流程；确认内容在成功后清除，操作失败则回滚用户凭据和确认状态。缓存锁用于协调同一 Telegram 的请求，账号关系以数据库为准，清缓存不解绑或重新重置。

消息记录按面板现有定时任务每天清理七天前的数据；超过七天的旧文本不会再次触发绑定。解绑确认本身短期且一次性有效。Telegram API 请求超时后，无法保证外部回复严格只发送一次，但重复投递不能重复改变绑定。

消息入口使用 Telegram 官方请求头密钥校验；出站请求使用 POST JSON，关闭订阅链接预览。日志不记录原始消息、完整链接、机器人密钥或带密钥的异常 URL。管理端审计仅记录操作和配置变更标志。
