## 建议优先修复

### 1. 共同连接参数遗漏 VLESS Encryption 校验

优先级：启用或混用 VLESS Encryption 时为高；全部关闭时不影响现有池。定位：面板 `app/Services/LoadBalancerService.php:49`，管理端 `src/features/load-balancer/poolConfig.js:51`。

这里的 VLESS Encryption 是节点编辑中独立的协议加密开关，对应 `protocol_settings.encryption`。自动统一 Reality 已覆盖 Reality 密钥对、短 ID、握手域名和端口，允许不同服务器使用同一个连接域名；该功能的用途和现有统一范围没有问题。本项只涉及另行开启的 VLESS 协议加密，全部成员均关闭该开关时，参数差异不会触发本项问题。本次没有检查生产池是否实际启用此开关。

两端只比较公网端口、流控和 Reality 参数，没有比较 VLESS 加密开关及客户端加密参数。两台 Xray 前置可以保持相同的 Reality 配置，同时一台关闭 VLESS Encryption、另一台开启，或两台使用不同的 VLESS 加密配置。

各节点自身配置校验允许这种合法的单节点设置，池的兼容性校验也不会指出差异。订阅入口参数取自一个前置，见 `app/Services/ServerService.php:143`；通用订阅实际输出该前置的客户端加密参数，见 `app/Protocols/General.php:176`。DNS 将用户分到另一台后，客户端配置可能与该台的解密要求不一致，造成握手失败。

已实际执行管理端兼容性函数，确认加密开关不同的两个节点返回空问题列表。后端存在同样的字段遗漏；没有运行实际握手验证。

建议把有效的客户端加密设置加入前后端兼容性校验。Reality 自动统一不应顺带覆盖 VLESS 加密设置。若要支持同池开启 VLESS Encryption，应明确校验各成员服务端解密设置与共同客户端参数是否兼容；无法可靠判断时先拒绝混用。

回归应覆盖开关不同、客户端参数不同、相同加密配置，以及关闭 VLESS 加密的原有池。

### 2. 增加前置成员时，没有反向检查现有落地链路

优先级：高。定位：`app/Services/LoadBalancerService.php:167`，对照 `app/Http/Requests/Admin/ServerSave.php:386`。

保存落地时会逐一检查各前置内核能否承载落地内部协议。反过来编辑前置池、增加成员时，只校验前置自身的 VLESS Reality TCP 设置，没有重新检查该池已绑定的落地及落地主备。

具体场景：原池只有 Xray 前置，已绑定内部使用 XHTTP 的 VLESS 落地；再增加连接参数一致的 sing-box 前置。新前置自身可以通过池校验，但 sing-box 内部中转不支持 XHTTP，见 `app/Services/ServerRelayService.php:543`。运行配置生成会过滤该成员无法承载的落地，见同文件 `:267` 和 `:195`；DNS 候选选择仍只检查前置自身，用户可能被分到没有对应可用中转线路的成员。

同一遗漏也影响 Agent 版本：已有启用的落地主备要求前置 Agent 至少为 v2.30.0；普通优先级池增加成员时仅要求 v2.25.0。新成员可能通过池保存，却无法执行既有落地主备。

建议保存池之前，在事务中检查所有关联落地及启用的主备成员，对每个新前置校验实际内核、协议和所需 Agent 版本；运行时仍保留失效保护。节点管理中直接更换前置内核时也应复用该检查，避免只修复池编辑入口。

回归应覆盖 Xray 池增加 sing-box、存在 XHTTP 或 VLESS Encryption 内部链路、已有落地主备时增加旧 Agent，以及失败时节点和池均不留下部分修改。

### 3. 离线会清空端口恢复确认状态

优先级：中。定位：`app/Services/FrontPoolScheduler.php:27`、`:36`、`:63`。

开启端口检查时，某地址连续两次失败会退出候选，原代码要求两次成功恢复。但成员离线、停用、连接参数不兼容或地址解析失败后，本轮参与端口循环的地址为空，保存的端口状态随之被覆盖为空。

成员再次在线且地址重新出现时，端口状态默认初始化为健康。此时即使第一次探测仍失败，也只有一次失败计数，地址仍重新进入候选；第一次成功也会立即加入，绕过两次成功恢复确认。

建议区分新地址初始化和既有失败地址恢复，保留仍属于成员配置的地址状态，地址变化时显式重置。为恢复中的成员建立明确的确认状态，避免用默认健康代替恢复确认。

回归应覆盖两次端口失败后离线再上线、解析失败后恢复、池停用再启用、IPv4/IPv6 分别恢复及首次新增地址。

## 可用性与交互改进

### 4. 一条个人解析未就绪，会使整份订阅失败

定位：`app/Services/DnsPoolService.php:127`、`app/Services/DdnsService.php:125`、`app/Http/Controllers/V1/Client/ClientController.php:86`。

池域名投影未就绪时直接抛出 HTTP 503；上层遍历多条线路没有隔离该异常。因此新用户尚未生成个人解析、某池初始化失败或同步写入处于未确认状态时，即使其他线路正常，整个订阅请求也会失败。应用配置入口同样调用该投影流程。

这是当前明确实现的失败行为，建议作为可用性设计改进处理。可以仅移除未就绪线路，保留正常线路；全部请求线路都未就绪时继续返回 503。用户无权使用整个订阅时仍按现有鉴权返回 403。需要同步评估客户端更新后暂时移除线路的体验，并验证订阅统计、筛选和节点数量保持正确。

### 5. 新建池更换首成员后，表单可能保留旧公钥

定位：管理端 `src/features/load-balancer/LoadBalancerPage.jsx:84`、`src/features/load-balancer/poolConfig.js:113`，面板 `app/Services/PoolRealityService.php:37`。

新建池先选择 A，再编辑握手域名或短 ID，会把 A 的公开参数保存到表单草稿，但不复制 A 的私钥。随后移除 A，让 B 成为首成员，成员变更不会重新处理草稿里的公钥。

提交时仍发送 A 的公钥，而服务端首次创建会取 B 的私钥作为来源，两者不匹配就拒绝保存。已有池保留已保存模板是正确行为；本问题仅针对尚未保存、没有明确输入或生成私钥的新池。

已执行辅助函数，确认上述草稿更换首成员后仍使用旧公钥。建议新池在没有明确指定私钥时，将密钥来源跟随首成员，保留用户主动编辑的握手域名和短 ID；不要改变已有池模板固定的行为。

## 需要专项验证的并发与规模风险

### 6. 固定锁租期与无上限同步时长不匹配

定位：`app/Services/BalancerDnsService.php:13`、`app/Services/PowerDnsService.php:18`、`app/Services/DnsPoolService.php:89`、`app/Console/Kernel.php:76`。

池锁租期为 120 秒，区域锁为 180 秒，没有续期或写入前的版本核对。同步一次性加载所有用户、别名和区域 RRset，首次创建记录和切换后确认分配采用逐条数据库写入；池之间顺序处理，同区域还会重复读取全区域记录。节点域名解析也缺少本轮总时长控制。

在大量用户、慢解析或数据库延迟下，执行时间可能超过租期。此时另一个保存、删除或同步操作可以取得同一锁，而前一个任务继续按旧配置写入 DNS 或保存候选状态，形成竞态。定时任务自身的防重叠租期也是两分钟，且该命令在调度进程中同步执行，慢任务会延后其他顺序任务。

这里已确认锁和循环的实现条件，但没有测得当前实际耗时超过租期，也没有运行多进程竞态复现，不应表述为生产已发生的问题。

建议先记录单池/区域耗时、用户数、记录数和 API 批次；按区域组织工作，避免每池完整读取相同区域；批量处理数据库意图和确认结果。引入受控任务时长、适当锁续期及配置版本检查，不能只延长固定租期。若将 DNS 写入拆批，必须先确保新成员解析可用，再改用户别名，最后删除旧成员，并保留每批的归属与重试状态。

## 问题 1–5 的修复与验证

面板 2.1.1、管理端 0.86.1 在本地未发布，包含原有 Reality 自动统一改动。

- 同池额外 VLESS Encryption 开关须一致；开启时校验客户端加密及服务端解密配置，关闭时忽略残留参数。Reality 自动统一继续使用原有范围。
