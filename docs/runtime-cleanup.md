# 运行数据清理

## 历史统计清理续跑（1.106.3）

[1.106.3 已正式发布](https://github.com/P0me1oo/YZboard/releases/tag/v1.106.3)，镜像与核验结果见[兼容矩阵](../YZ_COMPATIBILITY.md)。仅需更新面板，定时调度应保持运行；升级后没有已有待办时，由下次零点任务启动清理。

`reset:log` 仍每天零点启动。原实现每张表每轮最多删除 50,000 条，达到批次或时间上限即结束，剩余记录只能等到次日；当每天产生的到期记录超过这个上限时，分钟统计等历史会持续积压。

现在清理前先在设置表保存待续跑标记（`runtime_log_cleanup_pending`）。达到上限或执行失败时保留标记，调度器每五分钟通过 `reset:log --resume` 继续处理；完整检查一轮没有到期记录后才移除标记。没有待办时，续跑入口只检查标记，不扫描历史表。最后一批刚好达到上限时，会在下一次续跑确认清完。

每轮继续沿用每表每批最多 500 条、默认 100 批和 20 秒的预算；已完成的批次不回滚，失败批次可重试。手工指定的预算仅影响当前轮，自动续跑使用默认预算。预算只限制是否开始下一轮，不是单条 SQL 的硬超时。日常任务和续跑在后台执行，共用命令内的 30 分钟互斥锁，手工调用同样受保护；进程异常退出后，锁到期才允许继续。数据库标记不依赖缓存存活，重启或清空缓存后仍可续跑；定时调度必须保持运行。

各次续跑按执行时的面板时区重新计算边界：分钟只留当天、小时和入站 IP 历史留 30 个自然日、日汇总留 365 个自然日，管理员日志仍留三个月。用户套餐已用量、节点累计及上报防重记录不在此清理范围内。无需新增数据库迁移，管理端、Node 和核心保持不变；回退旧版本后恢复原来每天一次的清理，已删除的过期历史无法通过回退代码恢复。

此修改控制历史积压，不执行表重建，也不保证数据库文件立即缩小。

## 既有运行数据清理

面板 [`1.68.5`](https://github.com/P0me1oo/YZboard/releases/tag/v1.68.5) 已发布，配套管理端 `0.41.4`。清理优化不改变 Node、两个核心、页面交互和通信格式，正式版本同时纳入原 `1.68.4` 的统计返回位置与文案修改。双架构镜像、固定来源和验证结果见 [兼容矩阵](../YZ_COMPATIBILITY.md)。

## 修改原因

原来每分钟补报任务还会查找所有七天前已结算报告，并判断其详细内容是否已经清空。已清空的旧记录继续留在查找范围，清理工作随历史报告数量增长。

机器历史的旧 HTTP 上报入口随机清理一天前的数据，长连接入口没有对应清理。停止上报或改用长连接后，旧历史可能持续留存。Compose 样例也未设置容器日志容量上限。

参考 Komari 固定源码 `e48aa1e76931132fb5dc93ce53763dd59df83d9f` 的独立低频清理与时间索引思路。报告清理标记是针对 YZboard 防重复结算设计的实现，不照搬监控采样进入内存即可确认的处理方式。新增时间字段与索引本身会占用一些空间，主要用于减少重复读盘；本轮不删除永久防重记录，也不承诺报告表不再增长。

## 流量报告

流量报告是节点提交的用户与中转用量，不等于后台统计结果。此次只清空超过保留期的原报告详细内容，用户用量、节点累计和统计表保持原样。

- 结算事务同时保存七天后的详细内容清理时间（`payload_cleanup_at`）。失败或尚未结算的报告不进入到期清理。
- 时间为 `0` 表示尚未登记，正数为 Unix 秒时间，`null` 表示内容已清空。复合索引按结算状态、清理时间和记录编号定位；正常清理只查询成功且时间已到的记录，已清空记录不再参与候选读取。
- 清空内容与移除清理时间在同一次数据库更新中完成。报告所属节点、原编号及防重键、已处理状态永久保留；迟到补报和重复队列任务继续按原规则去重。
- 每分钟的 `node:retry-reports` 只负责重派未完成报告。独立 `node:prune-reports` 每小时整点运行，有单实例与防重叠调度保护。
- 清理与旧记录登记均每批最多 500 条，默认单轮最多 100 批。默认经过 20 秒后不再开始下一轮，已经开始的一批仍完成或失败返回，因此该时长不是数据库单条语句的硬超时。单轮最多分别登记 50,000 条旧报告、清空 50,000 条到期报告。
- 每轮先处理已有到期记录，再登记一批旧记录。新登记的到期记录可能在下一轮或下一次调度清空；积压超过限额时分多次调度消化，不承诺升级后立即清完。
- 每批事务完成后即保留进度。某批失败不撤销前面已完成的批次，失败批次仍留在候选范围，下一次调度可继续处理。清理不会刷新报告业务更新时间或结算时间。

## 旧数据、迁移与回退

迁移只新增报告清理时间、报告清理索引和机器历史时间索引，不在迁移中批量修改报告内容。新增索引仍需读取现有数据，不能保证大表建索引没有等待或额外磁盘占用。

已有报告默认清理时间为 `0`。后台按索引分批登记，仅选取成功且有结算时间的报告；已经没有详细内容的记录直接改为 `null`。有内容的记录按实际结算时间加七天登记，未结算或缺少结算时间的记录不清理。登记只读取编号、结算时间及是否存在内容，不把历史 JSON 内容载入 PHP 内存。

数据库保留默认值 `0`，旧版本程序忽略新增列时仍可正常插入。回退期间新插入或后来才完成结算的旧报告，会在再次运行新清理任务时登记。已清空的报告不会被重复登记，也不根据报告创建日期提前清理迟到结算。

回退旧代码可保留新增列和索引，无需删除业务数据；旧版本会恢复原来的清理方式及其扫描开销。清空的原报告内容和删除的机器历史无法通过回退代码恢复。新增迁移的回滚仅移除新增列和索引，不删除防重记录。

## 机器监控历史

- `machine:prune-history` 每小时第 30 分钟运行，与报告清理错开；使用记录时间和编号索引分批删除超过 24 小时的 CPU、内存、磁盘和网速采样。
- 默认每批 500 条、每轮最多 100 批，经过 20 秒后不再开始下一批。故障或积压时，下轮从最早剩余记录继续，不要求机器在线或继续上报。
- 旧 HTTP 上报入口不再随机执行删除；HTTP 与长连接统一由此任务维护。实时机器状态、最近在线时间和原有采样频率不变。
- 查询无论是否传入时间范围，都只展示最近 24 小时。恰好位于 24 小时边界的记录仍保留；用户仍可选择更短范围，最多读取 1,440 个采样点。
- 调度正常且没有积压时，过期记录通常在下一小时清理；积压、调度停用或执行失败可能延后物理删除，但查询不放宽保留范围。
- 删除后空间通常可供数据库复用，数据库文件不一定立即缩小。本次不执行数据库重整。

## 容器日志

四份 `compose*.sample.yaml` 增加以下容器日志配置：

```yaml
logging:
  driver: json-file
  options:
    max-size: "20m"
    max-file: "5"
```

每个容器最多保留约 100 MiB 的轮转日志；分拆部署的五个服务分别限制，合计约 500 MiB。最旧文件会被替换，不改变程序业务数据。Laravel 按日日志的配置仍为 14 天，其他单文件日志和任务监控的成功、失败记录保留规则未改动。

这是 Docker 的容器创建配置，无法由镜像自动修改。已有部署应在后续获准更新时由用户合入实际 Compose 并重建相应容器，不覆盖部署目录的其他配置、环境文件或挂载；本轮未执行这些操作。此片段只调整日志，镜像继续使用部署已确认的 YZboard 来源。

## 验证要求

- SQLite 与 MariaDB 严格分组模式的完整后端回归，检查报告结算与清理的事务、七天边界、旧数据登记、失败重试、重复上报、限量恢复及回退期间旧写入兼容。
- 机器历史检查 24 小时边界、不同机器、停用机器、限量恢复、删除失败重试、查询提前过滤及两种上报入口的统一保留规则。
- 使用独立合成数据核对新查询的索引和旧方案扫描差异，不读取或复制生产报告内容。
- 检查 Compose YAML 可解析及日志选项，运行现有管理端资源检查。没有改动管理端源码，不额外重建现有前端交付文件。
- 上线后在相近上报量下对比 CPU、数据库读盘、查询量、错误和日志增长；本地测试不能提供生产降幅。插件空任务先由用户重启面板后验证，本次不修改插件加载机制，也不调整数据库刷盘、PHP 缓存或进程数量。

## 本地查询验证

独立 SQLite 内存库与 MariaDB `11.4.8` 临时库分别生成 100,000 条合成报告，其中 99,995 条已清空、五条到期且仍有内容。没有复制生产报告或身份数据。

MariaDB 查询计划中，旧清理语句使用主键全索引扫描，估计检查 99,415 行；新候选查询使用清理时间复合索引，实际读取五行、访问两个索引页。SQLite 同样使用新索引的清理时间范围查找。新旧的候选识别规则针对同样的到期报告；旧方案没有因只有五条待清理而免除对其他历史的检查。

两种数据库都通过迁移升级、回滚和再次升级验证。报告记录与防重编号不被迁移删除，旧记录在升级后默认等待后台登记。完整后端与资源检查结果见兼容矩阵，不把合成查询的读行数变化换算成整机 CPU 或内存降幅。
