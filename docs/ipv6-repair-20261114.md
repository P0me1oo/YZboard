# 节点 IPv6 修复记录（2026-11-14）

维护者：P0me1oo。日期：2026-11-14（北京时间）。

本次通过 Lite MCP 修复 Taipei101-US Lax4、BreadCloud-US 的服务器网络配置，并恢复 Aether-US 的 ATT IPv6 客户端、调整其四个节点的出口配置。未修改面板或 Agent 程序，未升级产品版本。

## Taipei101-US Lax4

IPv4：`23.169.169.103`。原有 IPv6：`2602:f9a9:301:5e4d::1/48`，网关：`2602:f9a9:301::1`。

现场存在三层禁用：内核启动参数 `ipv6.disable=1`、系统参数关闭当前及新建接口的 IPv6、UFW 设置 `IPV6=no`。解除前两层并重启后，原有 Netplan 地址和路由正常加载，但防火墙仍仅允许 IPv6 回环流量，入站和出站默认均为丢弃。启用 UFW 的 IPv6 支持后，网关邻居解析与外网连接恢复。

| 文件 | 修改 |
| --- | --- |
| `/etc/default/grub` | 删除追加 `ipv6.disable=1` 的赋值及对应注释，执行 `update-grub` 并通过 `grub-script-check` |
| `/etc/sysctl.d/99-disable-ipv6.conf` | 将 `all`、`default`、`lo` 的 `disable_ipv6` 从 `1` 改为 `0` |
| `/etc/default/ufw` | 将 `IPV6=no` 改为 `IPV6=yes`，执行 `ufw reload` |

执行了一次系统重启，加载了机器此前已安装的 `6.12.116+deb13-amd64` 内核，重启前为 `6.12.113+deb13-amd64`；本次未安装内核或其他软件。保留原有 Netplan 地址与网关。UFW 继续默认拒绝 IPv6 新建入站连接，允许正常出站、已建立连接的回包及必要 ICMPv6；没有新增业务端口放行规则。防火墙重载前后的 IPv4 过滤规则经去除计数器和时间注释后完全一致。

## BreadCloud-US

IPv4：`217.217.45.201`。原生 IPv6：`2a06:9801:1e::18a/128`，网关：`2a06:9801:1e::1`。

机器还有附加地址 `2600:1700:3a90:c620:be24:11ff:fecd:6983/128`。修复前，默认连接选择该附加地址，IPv6 HTTPS 连接超时；显式绑定原生地址则立即成功。因此本次确认的问题是默认源地址选择，不能仅凭原检查结果认定原生 IPv6 上游故障。

在 `/etc/netplan/50-cloud-init.yaml` 的原生 IPv6 默认路由中新增：

```yaml
      - on-link: true
        to: "default"
        via: "2a06:9801:1e::1"
        from: "2a06:9801:1e::18a"
```

先用运行时路由验证，再执行 `netplan generate`，确认生成的主路由包含正确的 `PreferredSource`，通过 `networkctl reload` 和 `networkctl reconfigure eth0` 加载持久配置。重载后，主路由与实际 HTTPS 连接均使用原生地址。

保留原附加地址及 `99-attv6-custom.yaml`、`99-attv6-mtu.yaml`。显式绑定附加地址的连接仍会超时，本次恢复的是默认原生 IPv6 出口。BreadCloud-US 无需重启系统或 Agent。

## Aether-US

IPv4：`23.246.167.243`。原生 IPv6：`2602:faa8:502:c7::a/64`。检查时原生 IPv6 的 Cloudflare、Google HTTPS 连接均正常，但本机没有 ATT 地址、动态客户端配置、服务或旧版客户端文件。

供应商接口确认该虚拟机已登记，实验 IPv6 已启用且状态为 `ready`，分配了三个租约。因此问题在于本机尚未接入这些租约；同时面板中节点 `84`、`161`、`190`、`334` 的直连出站均强制 IPv4 并绑定 `23.246.167.243`，客户端即便请求 IPv6 字面地址，也会遇到出口地址族不匹配。

使用用户提供的[官方客户端地址](https://billing.aethercloud.io/dynamicv6/client.sh)，先下载、静态检查并核对两端文件 SHA-256，再执行安装，选择 `eth0` 和动态租约作为默认 IPv6 出口。检查时客户端文件的 SHA-256 为 `d051d095f611149e98fd49b6b900c951a368458c709ca4f648b135966ee499e8`。

持久服务为 `dynamicv6-next-guest.service`，已启动并启用开机启动；程序位于 `/opt/dynamicv6-next`，私有配置位于 `/etc/dynamicv6-next/guest.json`，租约与原生网络恢复依据位于 `/var/lib/dynamicv6-next-guest`。配置和状态文件权限均为 root 所有的 `0600`。客户端负责续租和动态地址、路由，不将租约地址写死到节点配置。

本次接入的三个 ATT 地址如下，后续以供应商当前租约为准：

- `2600:1700:443:580f:a::85d9`：本次选择的默认 IPv6 源地址。
- `2600:1700:322:8818:a::85d9`。
- `2600:1700:2bc1:409b:a::85d9`。

默认动态路由的 MTU 为 `1400`，优先级为 `99`。原生地址仍可显式绑定连接；动态租约不可用时，客户端保留原生 IPv6 恢复路径。

面板四个节点均继续使用 sing-box。通过应用模型事务保存下列出站参数，由原有配置通知机制下发，保留原 IPv4 源地址，允许 IPv6 优先和双栈连接回退：

```json
{
  "inet4_bind_address": "23.246.167.243",
  "domain_strategy": "prefer_ipv6",
  "fallback_delay": "300ms"
}
```

原先的参数为 `domainStrategy: ForceIPv4` 和 `send_through: 23.246.167.243`。保存前逐台核对内核、原出站及机器归属，避免覆盖并行修改。四个节点均回报配置更新成功，无需重启服务器或 Agent。IPv4 连接回退适用于能够解析出 IPv4 地址的目标，不会把 IPv6 字面地址转换为 IPv4。

## 回退依据

Lax4 的原状态为在 GRUB 末尾追加 `GRUB_CMDLINE_LINUX="${GRUB_CMDLINE_LINUX:+${GRUB_CMDLINE_LINUX} }ipv6.disable=1"`，三个 `disable_ipv6` 均为 `1`，UFW 为 `IPV6=no`。恢复这些值后需重新生成 GRUB、重载 UFW 并重启，结果会重新禁用 IPv6。

BreadCloud-US 的原路由没有 `from`。删除本次新增的这一行，重新生成并加载 Netplan 即可恢复原配置，但默认连接可能再次选中不可达的附加地址。

Aether 可通过供应商客户端的卸载入口恢复客户端记录的原生网络基线，再将上述四个节点的出站恢复为原先的 `ForceIPv4` 与单 IPv4 地址绑定。原生网络基线为客户端正式状态，应随服务保留，不能当作本次临时文件删除。

本次配置原件和检查中间文件仅置于任务专用 `/tmp` 目录，验证完成后清理；以上记录保留实际修改与回退依据。
